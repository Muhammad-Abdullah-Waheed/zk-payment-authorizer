Motivation

Why this problem matters

Autonomous AI agents increasingly perform value-bearing actions — bookings, subscriptions, cloud provisioning, financial automation. Today’s authorization models store spending rules in plaintext or rely on centralized controls, creating privacy, security, and auditability gaps.

Problem statement

Given a private user spending policy, an autonomous AI agent requesting a payment, and an on-chain verifier — how can the blockchain confirm policy compliance without revealing spending limits, approved vendors, time windows, or user secrets?

Our answer: a Noir zkSNARK proves all checks pass; the chain learns only the public claim (amount, vendor, time, policy hash, nullifier) plus “valid” or “invalid”.

Proposed solution

High-level workflow

ZK-AAPA issues UltraHonk proofs that a payment request complies with a private policy. The on-chain verifier checks the proof and the policy commitment but never learns policy details. Nullifiers prevent replay.

STEP 1

Policy setup

Owner defines spending_limit, approved_vendor_list, and allowed_time_window. A Poseidon2 commitment hash is registered on-chain.

STEP 2

Agent request

The AI agent composes a payment request (amount, vendor, timestamp) and submits it to the prover with the policy as a private witness.

STEP 3

Proof generation

The Noir circuit produces an UltraHonk proof of compliance and a unique nullifier; bb prove serializes the bytes for Solidity.

STEP 4

On-chain verification

PaymentAuthorizer checks registry, nullifier, then HonkVerifier.verify. Valid → authorization event; invalid → reasoned rejection.

Same 4-step pipeline as the original proposal — implemented end to end on a local Hardhat chain.

System architecture & technology stack

Three layers, one repo

Layer 1 — Frontend

React 19 + Vite. Five tabs: Status, Policy setup, Agent simulator, Quick demos, History. Talks to a Node API; signs txs through the simulator wallet.

Layer 2 — ZK proving engine

Noir circuit compiled with nargo 1.0.0-beta.21. UltraHonk proofs generated by Barretenberg bb 5.0.0-nightly.20260324 using the noir-lang/poseidon library.

Layer 3 — Blockchain

Solidity 0.8.28 (Cancun) on Hardhat. Three contracts: HonkVerifier, PolicyRegistry, PaymentAuthorizer.

ZK circuit design

Core constraints (Noir / Poseidon2)

Every check is enforced as a private constraint in circuits/payment_policy/src/main.nr. The verifier learns only that the checks passed.

Spending limit v1

payment_amount ≤ spending_limit via private witness arithmetic. spending_limit never exposed.

Time window v1

window_start ≤ current_time ≤ window_end. Window bounds remain private.

Vendor approval v1

Equality against a 4-slot private whitelist: vendor ∈ {v0..v3}. Merkle membership is a future upgrade.

Policy commitment v1

Poseidon2(limit, w_start, w_end, v0..v3) = policy_commitment binds the proof to a specific (registered) policy.

Replay prevention kept

nullifier = Poseidon2(tx_nonce). The on-chain contract stores accepted nullifiers and rejects reuse.

Hierarchical delegation (parent → agent → sub-agent) is on the roadmap; current circuit assumes one owner per policy.

Privacy model & security

What stays private, what goes on chain

Private (witness only)

  • spending_limit
  • tx_nonce (agent / user secret)
  • window_start, window_end
  • approved_vendor_0 .. _3

Used only during proof generation; never posted on-chain.

Public (on chain)

  • payment_amount
  • current_time
  • vendor address
  • policy_commitment (registered Poseidon2 hash)
  • nullifier
  • proof_bytes (~6.4 KB)

Security guarantees

Privacy preservation

Cryptographic authorization

Enforcement via zk-proofs, not trust in middleware.

Replay resistance

Unique nullifiers stored on-chain.

Novel contributions & research value

Why this PoC is more than a tutorial

End-to-end working prototype

Noir circuit → UltraHonk proof → Solidity verifier → PolicyRegistry + PaymentAuthorizer → React UI. 5 passing tests, benchmarks, and reproducible install.

Time-bound private policies

Window enforcement (start ≤ t ≤ end) inside the circuit; window bounds never leave the prover, defeating analysis of usage patterns.

Replay-resistant nullifiers

Poseidon2 over a private nonce; stored on-chain. Unforgeable and unenumerable.

Policy commitment registry v1

Separate PolicyRegistry contract whitelists Poseidon2 hashes of approved policies, decoupling policy life-cycle from payment authorization.

AI-agent focus

Designed for autonomous agents interacting with financial systems — least-privilege spending, public audit trail, owner-controlled policy rotation.

Smart contracts & frontend demo

What runs on the chain — and how to break it

Key contracts

  • PolicyRegistry.sol — registerPolicy(bytes32), isRegistered(bytes32).
  • PaymentAuthorizer.sol — authorize(bytes proof, bytes32[] pubInputs). Four guards: well-formed → registered → not replayed → Honk-verified.
  • UltraPlonkVerifier.sol — auto-generated HonkVerifier (optimized evm-no-zk).

Frontend (Vite + React)

  • Status — deployed addresses, registered policy, prebuilt proof.
  • Policy setup — edit limit / window / vendors, preview & register commitment.
  • Agent simulator — choose amount / time / vendor, prove + authorize.
  • Quick demos — 7 one-click failure scenarios.
  • History — every tx with gas, event, reason.

Challenges, performance & future work

What was hard, what we measured, what’s next

Technical challenges

  • Noir API churn between releases (legacy poseidon::bn254 → Poseidon2).
  • Matching bb ↔ nargo versions via bb-versions.json.
  • Cancun-only Solidity (mcopy) in the optimized verifier.
  • Keeping the public-input layout in sync across Noir, Solidity, and JS (scripts/policy.js :: PI).
